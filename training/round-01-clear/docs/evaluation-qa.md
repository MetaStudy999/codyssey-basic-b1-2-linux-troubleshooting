# B1-2 R01 — Evaluation Q&A Reference

실제 평가에서는 아래 기준 답안을 그대로 외우기보다 본인의 Runtime PID·수치·로그를 근거로 설명합니다.

## 1. Memory Leak과 OOM 계열 장애를 어떻게 구분·설명하는가?

메모리 누수는 더 이상 필요하지 않은 메모리 참조가 계속 유지되어 프로세스의 사용량이 시간에 따라 증가하는 현상입니다. B1-2에서는 `monitor.sh`의 MEM/RSS 추세와 애플리케이션 로그를 함께 보고, 단순 순간 사용량 증가가 아니라 시간에 따른 지속 증가와 보호정책 종료를 연결해 판단합니다.

## 2. 왜 MEMORY_LIMIT을 올리는 것은 근본 해결이 아닌가?

제한을 높이면 종료 시점을 늦출 수 있지만 누수 원인이 그대로라면 메모리는 다시 증가합니다. 근본 해결은 불필요한 객체/버퍼/컬렉션의 생명주기와 참조 유지 지점을 수정하는 것입니다.

## 3. 특정 프로세스 CPU Spike를 어떻게 확인하는가?

시스템 load만 보는 것이 아니라 Agent PID를 특정한 뒤 `ps -p PID -o %cpu` 또는 `top -p PID`로 해당 프로세스의 CPU 사용률을 추적합니다. B1-2 `monitor.sh`는 같은 PID의 CPU 값을 시간순으로 기록해 급상승 구간을 보여 줍니다.

## 4. 왜 Watchdog가 CPU 과점유 프로세스를 종료하는가?

하나의 프로세스가 CPU를 과도하게 독점하면 다른 서비스의 응답성과 시스템 안정성이 저하될 수 있습니다. 보호정책은 임계치 초과 시 해당 프로세스를 종료해 전체 시스템에 미치는 영향을 제한합니다. 실제 평가는 Watchdog/SIGTERM 로그와 CPU 수치를 함께 제시해야 합니다.

## 5. CPU_MAX_OCCUPY를 높이는 것도 왜 임시 조치인가?

임계값 상향은 종료 조건만 완화합니다. busy loop, 과도한 polling, 비효율적 알고리즘, 지나친 스레드/재시도 등 CPU를 사용하는 원인이 남아 있으면 문제는 반복됩니다.

## 6. 살아있지만 멈춘 프로세스를 어떻게 진단하는가?

1. `ps`/`kill -0`로 PID 생존 확인
2. monitor 로그로 CPU/MEM 변화 정체 확인
3. `top -H -p PID` 또는 `ps -L -p PID`로 스레드 상태 확인
4. 애플리케이션 로그가 어느 시점에서 멈췄는지 확인
5. WAITING/BLOCKED 관련 마지막 로그와 스레드 간 자원 대기 관계를 연결

프로세스가 죽은 장애와 Deadlock을 구분하는 핵심은 **PID는 유지되지만 유의미한 진행이 멈췄는지**입니다.

## 7. Deadlock의 4대 조건은?

- 상호 배제 (Mutual Exclusion): 한 자원을 한 번에 한 주체만 사용
- 점유 대기 (Hold and Wait): 자원을 가진 채 다른 자원을 기다림
- 비선점 (No Preemption): 다른 주체가 강제로 자원을 빼앗을 수 없음
- 순환 대기 (Circular Wait): A가 B를, B가 A를 기다리는 식의 순환 관계

B1-2에서는 최소한 상호 배제와 순환 대기를 실제 로그/스레드 관계로 설명할 수 있어야 합니다.

## 8. 로그에서 A → B, B → A 관계를 어떻게 추론하는가?

마지막 WAITING/BLOCKED 로그에서 각 스레드가 어떤 락/자원을 보유하고 무엇을 기다리는지 찾습니다. 서로의 보유 자원을 상대가 기다리는 순환이 보이면 Deadlock 추론 근거가 됩니다. 로그가 충분하지 않으면 `top -H`, `ps -L`은 정체 상태의 보조 증거이며, 락 관계 자체를 임의로 단정하면 안 됩니다.

## 9. OOM과 Deadlock이 동시에 의심되면 무엇부터 보는가?

먼저 시스템 전체 안정성과 증거 보존을 우선합니다. 메모리 고갈이 호스트 전체를 위험하게 만들고 있다면 자원 상태를 빠르게 확인하고 필요한 보호 조치를 취하되, 재부팅 전에 PID·메모리·스레드·로그를 가능한 범위에서 수집합니다. 그 다음 메모리 압박으로 인한 지연/정체와 실제 락 교착을 분리해 분석합니다.

## 10. 운영 환경에서는 monitor.sh를 어떻게 개선할 수 있는가?

단일 시점 출력보다 시계열 저장, 경고 연속 횟수, RSS 증가율, CPU 지속시간, 프로세스 재시작 횟수, 스레드 수, 알림 연동 등을 추가할 수 있습니다. 다만 R01에서는 공식 미션 통과에 필요한 증거 수집을 우선하고 과도한 운영 시스템 구축은 뒤로 미룹니다.

## 11. 세 장애의 코드 수준 근본 해결 예시는?

- Memory Leak: 객체 생명주기/참조 해제, 캐시 상한, 스트리밍, 불필요 데이터 누적 제거
- CPU Spike: busy loop 제거, backoff/sleep, 알고리즘 개선, 작업량 제한, 프로파일링
- Deadlock: 락 획득 순서 통일, 중첩 락 축소, critical section 최소화, timeout/try-lock, 공유 상태 감소

## 12. 임시 조치와 근본 해결을 왜 분리해서 써야 하는가?

환경변수 변경은 장애를 완화하거나 재현 조건을 바꾸는 Workaround일 뿐 결함 자체를 고치는 것은 아닙니다. 리포트에서 둘을 구분해야 운영자가 현재 위험과 장기 개선 과제를 혼동하지 않습니다.
